# UX MeasureLab 제품 기반 명세서

> **보존 상태:** 초기 제품 기반 기록이다. 현재 범위와 수용 기준은 [`../personal-product-v1/spec.md`](../personal-product-v1/spec.md)가 대체한다.

> **작성자:** Power-xc
> **작성일:** 2026-07-14
> **상태:** 검토 중

## 1. 왜 만드는가

개인 제품과 회사 프로젝트에서 행동 데이터는 여러 분석 도구에 흩어지고, KPI 정의부터 UX 가설·실험·결과 판정까지 수작업으로 이어져 제품 결정의 근거와 속도가 함께 떨어진다.

## 2. 누가 쓰는가

```text
주 사용자: 적은 트래픽의 실제 웹 제품을 만드는 Tech·AI Product Designer / AI Builder
보조 사용자: 스타트업 Product Designer, PM, Product Engineer
후속 사용자: 회사 신규 제품 팀과 Growth 담당자
```

## 3. 사용자가 얻는 단일 결과

제품 맥락과 행동 데이터를 넣으면, 가장 중요한 UX 문제 후보를 근거와 함께 확인하고 사전 기준이 정의된 다음 실험을 만든다.

## 4. 사용자 흐름

1. 사용자가 제품명, URL, 제품 단계, 대상 사용자, 핵심 가치 행동을 입력한다.
2. 시스템이 KPI 후보와 필요한 이벤트를 제안하고 사용자가 확정한다.
3. 사용자가 퍼널 CSV를 업로드하거나 샘플 데이터를 선택한다.
4. 시스템이 단계별 전환과 이탈을 계산하고 가장 큰 관찰 신호를 표시한다.
5. AI가 증거, 반대 증거, 대안 설명을 포함한 UX 가설 초안을 만든다.
6. 사용자가 실험 방법, 성공·실패·가드레일 기준을 확정한다.
7. 사용자가 결과를 입력하면 시스템이 수치 변화를 계산하고 AI가 제한된 판정 초안을 제시한다.
8. 사용자가 최종 결정을 기록하고 다음 실험으로 연결한다.

### 실패와 복구

- URL 분석 실패: 수동 제품 브리프 입력으로 전환한다.
- 잘못된 CSV: 오류 행과 필요한 열을 보여주고 재업로드를 제공한다.
- AI 응답 실패·지연: 결정적 계산 결과는 유지하고 템플릿 기반 수동 가설 작성을 제공한다.
- 근거 부족: 성공처럼 표현하지 않고 `insufficient_evidence`로 판정한다.

## 5. 제품 범위 선택지

| 옵션 | 초점 | 포함 | 제외 | 검증 |
|---|---|---|---|---|
| A. UX Audit | URL 기반 UX 진단 | 제품 브리프, KPI 초안, 정적 UX 가설 | 실제 정량 데이터와 결과 판정 | 첫 인사이트 생성 속도 |
| B. Measure Loop | 데이터에서 실험 결정까지 | URL·브리프, KPI, CSV 퍼널, 증거, 가설, 실험, 결과 | 실시간 연동, 자체 수집 엔진 | 완결된 첫 결정과 재방문 |
| C. Intelligence Platform | 통합 제품 분석 | PostHog·Clarity·Stripe 연동, 조직 기능 | 자체 리플레이 엔진 | 넓지만 초기 검증 비용 큼 |

### 권장안

옵션 B를 권장한다. A는 AI의 정적 조언에 머물러 제품의 핵심인 정량적 검증을 증명하지 못하고, C는 통합 개발이 핵심 가치 검증을 지연시킨다.

## 6. 이번에 하는 것

- 개인 워크스페이스와 한 종류의 프로젝트.
- 제품 브리프 입력 및 확인.
- KPI Tree 초안과 사용자 확정.
- 정해진 스키마의 퍼널 CSV 업로드.
- 전환율과 이탈률의 결정적 계산.
- Evidence Card와 대안 설명이 포함된 Hypothesis Card.
- 실험 사전 등록.
- 결과 입력, AI 판정 초안, 사람의 최종 Decision Log.
- UX MeasureLab 자체를 첫 도그푸딩 프로젝트로 제공.

## 7. 이번에 하지 않는 것

- 자체 이벤트 수집 SDK.
- 자체 히트맵과 세션 리플레이.
- 실시간 PostHog·Clarity·GA4·Stripe 연동.
- 기능 플래그와 A/B 대상 배정.
- 조직 초대·역할·결재.
- 자동 Figma 또는 Jira 변경.
- 관찰 데이터만으로 인과관계 단정.
- 교정 근거 없는 AI 신뢰도 백분율.

## 8. 성공 기준

- [ ] 신규 사용자가 15분 안에 프로젝트와 첫 KPI 계획을 확정한다.
- [ ] 유효한 5단계 퍼널 CSV에서 모든 단계의 전환율과 이탈률을 계산한다.
- [ ] 가장 큰 이탈 신호가 원인 아닌 관찰로 표시된다.
- [ ] 모든 AI 가설에는 근거, 대안 설명, 누락 근거가 존재한다.
- [ ] 실행 전 실험에 Primary Metric, 성공, 실패, Guardrail 기준이 존재한다.
- [ ] 최종 판정은 `support`, `partial_support`, `not_supported`, `insufficient_evidence` 중 하나다.
- [ ] AI 권고와 사용자의 최종 결정이 별도 기록된다.
- [ ] 첫 파일럿 사용자 중 두 번째 의사결정을 기록한 비율을 측정한다. 목표값은 파일럿 전 별도 확정한다.

## 9. 제약조건

- TypeScript만 사용하고 `any`를 금지한다.
- 외부 입력과 AI 구조화 출력은 런타임 검증한다.
- 계산 가능한 숫자는 코드가 계산하고 AI가 계산값을 만들지 않는다.
- 서버 시크릿을 클라이언트에 노출하지 않는다.
- 원본 리서치의 불완전한 인용 토큰을 검증된 출처처럼 사용하지 않는다.
- 사용자 행동 원본과 세션 리플레이는 MVP에서 수집하지 않는다.

## 10. 기술 설계로 넘길 열린 질문

- [ ] Next.js + Supabase를 MVP 기준 스택으로 승인할지.
- [ ] 초기 AI provider를 하나로 고정할지 adapter 경계만 만들지.
- [ ] MVP 인증을 포함할지, 단일 로컬 사용자 도그푸딩부터 할지.
- [ ] 배포 전까지 수집할 최소 개인정보 범위를 확정할지.
- [ ] 디자인 방향을 분석 도구형과 실험 노트형 중 어느 쪽으로 잡을지.

## 11. 확인된 사실과 가정

### 확인된 사실

- 사용자는 개인 제품과 회사 프로젝트에서 반복 사용할 제품을 원한다.
- KPI, 퍼널 이탈, UX 가설, 실험, 정량 결과 도출이 핵심이다.
- 사용자는 Tech·AI Product Designer 포트폴리오로도 활용하려 한다.

### NOT_CHECKED 가정

- CSV 기반 첫 버전만으로 반복 사용 가치를 검증할 수 있다.
- 개인 빌더가 첫 핵심 사용자로 가장 적합하다.
- KPI 제안보다 결과 판정 흐름이 더 높은 재방문을 만든다.
- 15분 이내 첫 KPI 확정이 적절한 시간 목표다.
